# 002 决策记录：为什么是"两个 Markdown 文件 + 冻结快照"

> 每条 ADR 四段式：**决策 / 理由 / 备选方案 / 影响**。末尾为未决问题表（U-n，负责人 + 默认处理）。

## ADR-1 否决 SQLite / embedding / 自动抽取 / 分域

**决策**：记忆的唯一权威源是共享根下的 `SOUL.md` 与 `MEMORY.md`。不建表、不做 embedding 与向量检索、不做自动抽取队列、不注册记忆专用 LLM 工具、不做群/用户分域（`spec.md` 非目标 N1–N5）。

**理由**

1. 规模不匹配：单进程、单用户，量级几千行文本；SQLite 的事务/索引/并发收益换不来成本。
2. 用户可见性本身就是目标（场景 S4）：文件能 `Get-Content`、能 `git diff`、能直接编辑；DB 里的条目用户看不到也删不掉。
3. 可迁移：记忆随共享根走，换机器 = 拷一个目录，无需导出/导入脚本与 schema 版本对齐。
4. 组件数 = 失败面：原方案要自建 schema 与迁移、维护抽取 worker 与重试、处理 embedding 供应商与索引重建、设计 scope 路由与越权边界，四套子系统各自能独立坏掉。
5. 用户已明确推翻原设计稿第 6 章（记录见 `specs/README.md` §6）。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| 原设计稿 §6：插件目录下 SQLite（WAL）+ `memory/*.md` 镜像 | 双写一致性；用户无法直接编辑权威源；迁移需脚本 |
| 写 AstrBot 主库新表 | 插件无 migration 钩子（`../_investigation/plugin-surface.md` §4.5），风险高 |
| 插件 KV（`put_kv_data`）/ 纯 embedding 检索 | KV 不支持检索与 diff；embedding 仍引入供应商依赖 |

**影响**

- 将来反悔要改：新增 `memory.py`（表/索引）、`extract.py`（队列 + 记忆 LLM）、`migrate.py`（解析 `- [日期] [来源] 内容` 入库），把 `render()` 换成"检索 + 渲染"；注入层与可见性层可原样保留（快照变成"检索结果的冻结缓存"）。
- 代价：无全文检索/相似度排序（只能 `astrbot_grep_tool` 关键词）；写入质量依赖守则而非 schema（ADR-5）；文件会膨胀（ADR-6）。

## ADR-2 对话级冻结快照，而不是每轮注入

**决策**：每个对话在**第一次** LLM 请求时渲染一次快照，之后该对话内复用同一字符串；键 = `umo + conversation_id`（`spec.md` FR-3）。不刷新、不做写后失效、不做定时重读；唯一换新入口是 `/new`（换 `cid`）。

**理由**

1. 成本：块在对话内逐字节稳定 → 整段 `system_prompt` 稳定 → 前缀缓存命中；否则每轮都变，缓存全废。
2. 行为可解释：同一对话内模型看到的记忆不变，不会"聊到第 5 轮突然忘了第 1 轮记得的事"，也不会因用户手改文件而在对话中途换性格。
3. 省 IO：命中路径 0 次文件读（NFR-1），把"要不要重读"从热路径上拿掉。
4. 心智一致：`/new` = 重新开始 = 重新读记忆，用户已有这个直觉。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| 每轮重读重渲染 | 缓存全废、成本随轮数上升、行为抖动 |
| `extra_user_content_parts` + `TextPart(...).mark_as_temp()` | `mark_as_temp()` 只设 `_no_save`（"provider-facing only, not persisted"，`agent/message.py:68-71`），`context.py:254` 定位为 per-turn context；语义是"本轮提示"而非"对话级冻结"。详见 `plan.md` §4.4 |
| 定时刷新 / `/astral refresh` | 引入时间维度、行为不可预测；与 N7 冲突；`/new` 已覆盖需求 |

**影响**

- 陈旧是**设计内**行为：手改文件后同对话看不到，须 `/new`（R-1）。
- `/reset` 只清历史、不换 `cid`（`builtin_commands/commands/conversation.py:110-141`）→ **不刷新快照**，须在 `show` 与文档中说明（U-7）。
- 长对话需要最新内容时，由 agent 自己 `astrbot_file_read_tool`；守则要求"改写前先读文件"（FR-4）。

## ADR-3 全局单份，而不是按群/按用户分域

**决策**：所有平台、所有群、所有私聊共享同一份 `SOUL.md` 与 `MEMORY.md`；无 scope 参数、无按 umo 的子文件、无群记忆目录。

**理由**

1. 与产品前提一致：001 的目标就是"所有平台/所有群共享同一个工作区根"，记忆跟着工作区走才自洽。
2. 复利：群 A 定的约定群 B 也能用；分域后每个群都要重新教一遍。
3. 实现与解释成本最低：无 scope 解析、无跨域读取规则、无"为什么它记得 A 不记得 B"的解释负担。
4. 用户已明确要求不分域。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| 按 umo 分域（每群一份） | 与共享工作区目标冲突；文件数随群增长；无法跨群复利 |
| global + group 双层 / 按主题分文件 | 多一层"写哪、谁赢"的决策与 scope 解析；单文件 + 小节结构已够用 |

**影响**

- 隐私边界 = 全局公开 → 三处披露（FR-7/AC-7.1）+ 守则禁止清单。
- 群聊指令默认不输出全文，只给元信息（FR-6/U-5）。
- 单文件必然膨胀（ADR-6）；跨 umo 并发写无锁，最坏丢一次追加（R-3）。

## ADR-4 不提供记忆专用工具，复用内置文件工具

**决策**：不注册 `memory_save` / `memory_search` / `memory_forget` 之类 `@filter.llm_tool`；agent 用 `astrbot_file_read_tool`、`astrbot_file_write_tool`、`astrbot_file_edit_tool`、`astrbot_grep_tool`（`fs.py:327/448/553/684`）读写记忆。

**理由**

1. 工具越多，模型选错工具的概率越高；记忆就是"读文件/改文件"，不需要新动词。
2. 内置工具已处理路径解析（相对路径以工作区根为基准，`fs.py:377,480,596,867`）与权限（`filesystem_scope`，`computer_tools/util.py:92-199`），自造要重实现且易与权限策略打架。
3. `@filter.llm_tool` 的参数 schema 从 docstring `Args:` 段解析（原设计稿 §6.5 已记录该坑），少一个这样的面就少一类问题。
4. 可复核：日志/轨迹里看到的是通用文件操作，用户能直接判断改了什么；将来改回 SQLite 只需换写入目标，守则与调用模式不变。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| `memory_save(content, key)` 专用工具 | 需自设去重键与格式校验；用户无法直接编辑；与文件并存会互相覆盖 |
| `memory_note` 写队列（异步落盘） | 引入队列与 worker，正是 ADR-1 否决的形态 |
| 专用工具 + 文件工具并存 | 两条写入路径的冲突规则无法解释 |

**影响**

- 写入质量完全依赖守则（FR-4）：格式、去重、容量、禁止项都写在托管区段里。
- 无结构化查询与自动去重，只能靠 `grep`；重复条目靠守则"先搜再合并"约束。
- 整文件覆盖风险由守则禁止 + `file_edit` 局部替换限制；若用户关闭本地文件工具（`computer_use_runtime=none`），写入能力同时失效——可接受降级。

## ADR-5 写规则放进 `EXTRA_PROMPT.md` 托管区段

**决策**：把"何时写、怎么写、写 SOUL 的门槛、容量、禁止项"写进共享根 `EXTRA_PROMPT.md`，用 `<!-- astral:managed:begin -->` / `end` 包裹；Astral 每次启动只重写标记之间，标记之外归用户（`spec.md` FR-4）。

**理由**

1. core 只读 `EXTRA_PROMPT.md` 这一个魔法文件（`astr_main_agent.py:451-486`，调用点 `1085` 无条件执行），**不读** `AGENTS.md` / `SOUL.md` / `MEMORY.md`（全仓库检索确认）→ 不需要打补丁就能生效。
2. 规则在盘上：用户能读、能 diff、能加自己的规则；出问题能直接看到"它被要求怎么做"。
3. 韧性：即使 `on_llm_request` 故障或被关，守则仍由 core 注入——"规则在、快照没了"好过"两个都没了"。
4. 托管区段解决"程序维护 vs 用户自定义"：区段内可整体重写与版本升级，区段外字节不动。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| 独立 `ASTRAL_RULES.md` + 自己注入 | 依赖钩子在场；与 core 注入顺序竞争；插件停用即失效 |
| 整文件覆盖 `EXTRA_PROMPT.md` | 会吃掉用户已有的工作区规则（该文件是 AstrBot 生态的公开约定） |
| 守则塞进快照头部 / 用 persona 承载 | 不可见不可编辑、每次改文案都要改格式；与 persona 管理冲突且不随工作区走 |

**影响**

- 必须处理标记容错（缺失→追加；异常→不写+报错），否则会毁用户规则（FR-4、AC-4.1）。
- 区段内手改会被覆盖，须在只读页与 `show extra` 披露（R-6）。
- 守则文案成为事实上的产品行为，改动要同步 `spec.md` FR-4 清单与 T-11。

## ADR-6 容量与截断：保留头部 + 显式提示，不自动归档

**决策**：注入预算 `SOUL 4000` / `MEMORY 8000` 字符；`MEMORY.md` 容量软上限 20000 字符；超预算保留头部并追加"已截断 + 绝对路径"，截断时附最多 10 条 `memory/archive/` 索引；**不自动搬移、不自动删除、不自动摘要**（FR-5）。

**理由**

1. token 成本可预测，不随文件增长失控（NFR-3）。
2. 保留头部符合书写约定（"身份在前、最新条目在前"），被截掉的通常是该进归档的历史尾部。
3. 自动归档是状态机：谁触发、阈值、失败回滚、归档后是否重写索引——一步错就丢数据，收益只是省一次手工剪切。
4. 显式提示把决定权交回 agent/用户：上下文里直接写着原文长度与全文路径，模型能自己决定要不要读。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| 不截断，注入全文 | 挤爆上下文，模型报错或价格失控 |
| 用 LLM 摘要压缩 / 自动搬进归档 | 摘要需额外调用（ADR-1 否决形态）且不可审计；自动移动破坏"文件由 agent/用户掌握" |
| 硬性拒绝超限写入 | 写入走 core 文件工具，插件拦不住，只能事后提示 |

**影响**

- 超长文件尾部在快照里不可见，须靠提示行指路（AC-5.2 断言路径存在）。
- 守则要求"最新在前"与"超 20000 先归档"，否则截断会切掉新内容（T-13）。
- 预算与软上限均可配（U-3/U-4），小上下文模型可下调（U-9）。

## ADR-7 与 AstrBot persona 的关系：分层优先级并写进快照

**决策**：不读取、不修改、不替代 persona。冲突按固定分层：**平台安全策略 > SOUL 的边界 > persona > SOUL 的身份与语气 > MEMORY 的事实 > 托管守则**（FR-1），该声明**写进快照正文**。

**理由**

1. persona 是用户显式选择、可按会话切换并由 AstrBot 管理；覆盖它等于让用户的选择失效。
2. SOUL 的边界只该收紧不该放松；让 persona 突破边界会出现安全事故（AC-1.2 就断言这点）。
3. 事实与人格分离：MEMORY 记录"发生了什么"，不应改变"它是谁"。
4. 位置偏差需抵消：快照在 `system_prompt` 末尾，尾部权重更高；不写清优先级，模型会自然偏向最后读到的 SOUL/MEMORY 而压过 persona。

**备选方案**

| 方案 | 未采用原因 |
| --- | --- |
| SOUL 完全覆盖 persona | 用户的 persona 选择失效，与 AstrBot 交互习惯冲突 |
| persona 覆盖 SOUL / 不写优先级靠模型权衡 | 边界可被人设突破；行为不可预测、AC-1.2 无法断言 |
| 运行时检测冲突并提示 | 自然语言冲突无法可靠检测，只产生噪声 |

**影响**

- 快照头部固定两行优先级声明成为格式的一部分（`plan.md` §4.1）；改这条要同时改模板与 AC-1.2。
- 用户会看到"语气跟着 persona 变、边界不跟着变"，须在用户文档解释（T-17）。
- 若将来引入多 persona / 多 SOUL，分层需重新讨论（当前明确为单 SOUL + 单 persona 选择）。
